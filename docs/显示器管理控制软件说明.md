# ScreenTools 显示器管理控制软件说明

> 基于 Windows 系统接口的本机显示器控制方案  
> 参考项目：[LGwebOS-menubar](https://github.com/gabrielgreco1/LGwebOS-menubar)  
> 文档版本：1.0  
> 更新日期：2026-10-17

## 1 文档结论

ScreenTools 定位为 Windows 原生显示器控制中心。软件常驻系统托盘，直接读取和修改本机显示配置，并通过 Windows 提供的监视器配置接口控制支持 DDC/CI 的外接显示器。核心功能不依赖电视厂商账号、云服务或局域网配对。

首个版本应优先实现：

- 多显示器识别和热插拔响应
- 分辨率、刷新率、方向和主屏设置
- 扩展、复制和单屏拓扑切换
- 外接显示器亮度和对比度控制
- 配置方案保存和一键应用
- 托盘快速面板和全局快捷键
- 本地诊断日志和失败恢复

Windows 显示配置接口负责桌面拓扑和显示模式。外接显示器的亮度、对比度、音量、输入源和电源状态通常通过 DDC/CI 访问。显示器、显卡驱动、扩展坞和连接方式会影响可用能力，因此软件必须先探测能力，再显示或启用对应控件。

## 2 参考项目分析

[LGwebOS-menubar](https://github.com/gabrielgreco1/LGwebOS-menubar) 是一款 macOS 菜单栏应用，通过局域网控制 LG webOS 电视。项目使用 SwiftUI 和 AppKit 构建浮动控制面板，以 `RemoteStore` 集中管理界面状态和业务操作，并通过加密 WebSocket 完成电视配对和命令传输。

项目现有能力包括：

- SSDP 局域网电视发现
- WebSocket 配对和证书指纹固定
- 应用启动和 HDMI 输入切换
- 方向键、触控板和文本输入
- 音量、静音和媒体控制
- 画面参数读取与修改
- Wake-on-LAN
- 本地使用时长和操作日志
- DLNA 媒体投送
- 离线自检和隐私检查

ScreenTools 不复用 webOS 网络协议，而是借鉴以下设计：

| 参考项目设计           | 可复用思路               | ScreenTools 调整                                   |
| ---------------------- | ------------------------ | -------------------------------------------------- |
| 菜单栏浮动面板         | 控制入口常驻且低打扰     | 改为 Windows 系统托盘面板                          |
| `RemoteStore` 集中状态 | UI 只订阅状态并调用动作  | 建立 `DisplayStore` 和命令调度层                   |
| 连接与能力状态         | 控件根据当前状态启用     | 根据系统路径和 DDC/CI 探测结果启用                 |
| 操作日志与自动恢复     | 故障可解释，断线后可重试 | 监听显示器热插拔并重新枚举，失败时回滚             |
| 本地存储与隐私         | 不依赖账号或云端         | 配置方案和日志仅保存在用户目录                     |
| webOS 协议适配器       | 设备通信与界面隔离       | 替换为 Windows CCD 和 Monitor Configuration 适配器 |

| 分类     | 功能                                                       |

- 远程电视发现和 IP 地址配对

- 显卡驱动控制面板中的厂商私有功能

## 4 用户场景

- 桌面办公用户同时调整两台或更多显示器的亮度，并快速切换扩展、复制和单屏模式。
- 开发与设计用户在不同分辨率、刷新率、方向和显示器位置之间切换。
- 笔记本用户接入扩展坞后自动应用办公配置，拔出后恢复移动配置。
- 会议与演示用户一键将指定屏幕设为主屏，或切换为复制模式。
- 使用多输入显示器的用户在电脑、游戏机和其他输入源之间切换。

## 5 功能设计

### 5.1 设备概览

主面板按物理显示器展示卡片。每张卡片显示：

- 显示器名称和用户别名
- 当前分辨率和刷新率
- 屏幕方向
- 主屏和活动状态
- 连接技术
- HDR 状态
- DDC/CI 可控制能力

显示器标识优先由适配器 LUID、目标 ID 和设备路径组合生成，避免仅依赖容易变化的显示序号。对于相同型号的多台显示器，应结合 EDID 信息和设备路径进行匹配，并允许用户设置别名。

软件需要响应以下事件：

- 显示器接入或断开
- 笔记本休眠和唤醒
- 扩展坞接入或拔出
- 显卡驱动重新配置
- 分辨率或拓扑被其他程序修改

能力探测失败时仍应展示设备和系统配置项，只隐藏或禁用对应硬件控件。

### 5.2 显示模式和拓扑

软件读取当前显示路径、源模式和目标模式，允许用户修改扩展、复制、仅电脑屏幕和仅外接屏幕等拓扑。

| 控制项         | 系统实现                         | 安全规则                       |
| -------------- | -------------------------------- | ------------------------------ |
| 分辨率和刷新率 | 读取系统可用模式并提交目标模式   | 只允许系统返回且适合桌面的模式 |
| 方向           | 设置目标路径旋转值               | 旋转后重新计算宽高和相邻位置   |
| 显示器位置     | 更新源模式坐标                   | 禁止重叠并保留至少一个可见屏幕 |
| 复制与扩展     | 构造并提交显示路径集合           | 提交失败时保持原配置           |
| 主显示器       | 调整桌面坐标原点和路径配置       | 保证目标显示器处于活动状态     |
| HDR            | 读取高级颜色能力并按系统支持设置 | 不支持时不显示开关             |

显示器位置调整应在一次配置事务中提交，避免逐项修改引起窗口跳动或多次黑屏。

### 5.3 亮度和硬件控制

外接显示器控制通过 Windows Monitor Configuration API 访问 DDC/CI。软件先取得物理显示器句柄，再读取能力标志和能力字符串。

实现规则：

- 亮度、对比度和色温优先使用 Windows 高层监视器接口。
- 输入源、音量和电源等扩展功能使用经过白名单限制的 VCP 代码。
- 滑块使用短延迟合并写入，避免拖动时持续发送 DDC/CI 命令。
- 每台显示器使用独立串行队列，避免设备通信互相阻塞。
- 读取失败时保留最近一次成功值并标记为未确认，不伪造默认值。
- 联动亮度时，分别按每台显示器的最小值和最大值换算百分比。
- 所有物理显示器句柄都必须及时释放。

DDC/CI 不是所有显示器都能可靠支持。USB 显示器、部分扩展坞、电视和未完整实现 MCCS 的设备可能不支持相关控制，或返回不准确的能力信息。

### 5.4 配置方案

配置方案保存可恢复的用户意图，而不是保存临时句柄。

一个配置方案包含：

- 目标显示器匹配规则
- 扩展、复制或单屏拓扑
- 显示器位置
- 主显示器
- 分辨率和刷新率
- 方向和 HDR 状态
- 已验证的亮度、对比度和输入源等硬件参数

示例方案：

| 方案 | 触发方式             | 示例内容                             |
| ---- | -------------------- | ------------------------------------ |
| 办公 | 托盘菜单或连接扩展坞 | 双屏扩展、外接屏为主屏、亮度 65%     |
| 会议 | 快捷键               | 复制模式、关闭 HDR、演示屏使用 60 Hz |
| 夜间 | 手动或计划任务       | 所有可控显示器亮度 25%、降低对比度   |
| 游戏 | 快捷键               | 主显示器高刷新率、切换指定输入源     |

### 5.5 托盘和完整设置界面

| 区域         | 内容                                  | 主要操作                         |
| ------------ | ------------------------------------- | -------------------------------- |
| 托盘快速面板 | 显示器卡片、亮度、当前方案和快速拓扑  | 调整亮度、应用方案、打开完整设置 |
| 显示器详情   | 模式、方向、HDR、能力和设备标识       | 修改单台显示器参数               |
| 布局编辑器   | 按实际比例显示屏幕矩形                | 拖动位置、选择主屏、切换复制关系 |
| 方案管理     | 方案列表、包含的设置和匹配条件        | 新建、更新、应用、导入和导出     |
| 诊断         | 系统路径、DDC/CI 能力、错误和操作记录 | 复制脱敏报告、重新探测           |

## 6 技术架构

项目采用 `pnpm + pnpm workspace + Electron + Vue 3 + TypeScript`。Electron 主进程负责应用生命周期、系统托盘、全局快捷键、配置持久化和原生显示控制；Vue 渲染进程只负责界面展示与用户交互；预加载脚本通过受控 IPC 暴露最小能力集合。

Windows 显示配置和 DDC/CI 属于 Win32 能力，生产版本建议通过 Node-API 原生模块封装。原生模块只在 Electron 主进程中加载，并由 TypeScript 服务层统一管理句柄、超时、错误码和任务队列。渲染进程不得直接加载原生模块，也不得获得 Node.js 文件系统或进程权限。

```text
系统事件
   ↓
设备枚举
   ↓
能力探测
   ↓
状态合并
   ↓
DisplayStore
   ↓
用户界面和命令调度
   ↓
变更计划验证
   ↓
系统配置提交和 DDC/CI 写入
```

### 6.1 分层设计

| 层级            | 职责                                        | 建议组件                                            |
| --------------- | ------------------------------------------- | --------------------------------------------------- |
| Vue 渲染层      | 托盘面板、布局编辑器、设置和诊断            | Vue 3、TypeScript、Pinia                            |
| 预加载层        | 向渲染进程暴露类型安全的最小 API            | Electron `contextBridge`                            |
| Electron 主进程 | 生命周期、托盘、快捷键、IPC、命令编排和通知 | Electron Main、`DisplayStore`、`CommandCoordinator` |
| 领域层          | 状态模型、方案匹配、变更计划和回滚规则      | 纯 TypeScript workspace 包                          |
| 系统显示层      | 枚举路径、读取模式、提交拓扑和监听变化      | TypeScript facade 和 Node-API addon                 |
| 物理显示器层    | 句柄生命周期、能力探测和 DDC/CI 读写        | Node-API addon 和每设备任务队列                     |
| 持久化层        | 设置、方案、设备别名和日志                  | JSON 文件、本地滚动日志、Schema 迁移                |
| 基础设施层      | 单实例、自动启动、更新、打包和错误报告      | Electron API、`electron-builder`                    |

### 6.3 Electron 进程边界

```text
Vue Renderer
  只能调用 window.screenTools
        ↓
Preload

        ↓
IPC Main
  校验 channel 和 payload
        ↓
TypeScript Services
  状态管理 方案匹配 任务调度
        ↓
Native Bridge
  QueryDisplayConfig SetDisplayConfig DDC/CI
```

安全配置：

- `contextIsolation: true`
- `nodeIntegration: false`
- 渲染进程启用 sandbox
- IPC 请求和返回值使用共享 TypeScript 类型，并在运行时使用 Schema 校验
- IPC channel 使用固定枚举，不接收任意方法名、路径或命令
- 原生模块仅由主进程加载
- 所有 DDC/CI 写入由主进程串行调度

### 6.5 原生桥接边界

`packages/display-native` 对外只导出稳定、窄范围的方法，不把 Win32 句柄或结构体直接传给 TypeScript。

```ts
export interface NativeDisplayBridge {
  querySnapshot(): NativeDisplaySnapshot
  validateDisplayPlan(plan: NativeDisplayPlan): NativeValidationResult
  applyDisplayPlan(plan: NativeDisplayPlan): NativeApplyResult
  enumerateMonitorCapabilities(): NativeMonitorCapabilities[]
  readMonitorFeature(request: NativeFeatureRequest): NativeFeatureResult
  writeMonitorFeature(request: NativeFeatureWriteRequest): NativeWriteResult
}
```

原生层返回可序列化 DTO 和明确错误码。TypeScript 层负责将错误码转换为用户可理解的信息，并决定是否重试、降级或回滚。

## 7 Windows 系统接口映射

| 需求               | Windows 接口                                                       | 实现要点                                |
| ------------------ | ------------------------------------------------------------------ | --------------------------------------- |
| 枚举活动显示路径   | `GetDisplayConfigBufferSizes` `QueryDisplayConfig`                 | 处理 `ERROR_INSUFFICIENT_BUFFER` 并重试 |
| 读取名称和首选模式 | `DisplayConfigGetDeviceInfo`                                       | 读取目标名称、设备路径和首选模式        |
| 提交拓扑和模式     | `SetDisplayConfig`                                                 | 先验证再应用，按需写入系统持久配置      |
| 枚举逻辑显示器     | `EnumDisplayMonitors`                                              | 建立桌面显示区域与系统路径的映射        |
| 枚举物理显示器     | `GetPhysicalMonitorsFromHMONITOR`                                  | 一个逻辑监视器可能对应多个物理句柄      |
| 能力探测           | `GetMonitorCapabilities` `CapabilitiesRequestAndCapabilitiesReply` | 缓存结果并允许用户重新探测              |
| 亮度               | `GetMonitorBrightness` `SetMonitorBrightness`                      | 按设备真实范围换算百分比                |
| 对比度             | `GetMonitorContrast` `SetMonitorContrast`                          | 按设备真实范围换算百分比                |
| 扩展 VCP 控制      | `GetVCPFeatureAndVCPFeatureReply` `SetVCPFeature`                  | 只开放已确认安全的代码                  |
| 设备变化           | `WM_DISPLAYCHANGE` 和设备通知                                      | 去抖后完整重新枚举并合并状态            |

`QueryDisplayConfig` 返回显示路径、源模式和目标模式。设备名称、设备路径和首选模式可通过 `DisplayConfigGetDeviceInfo` 补充读取。拓扑修改应优先通过 `SetDisplayConfig` 一次提交。

## 8 关键工作流程

### 8.1 启动和重新枚举

1. 查询活动显示路径和模式。
2. 读取每个目标的设备名称、设备路径和首选模式。
3. 将系统显示目标映射到逻辑监视器和物理监视器句柄。
4. 并发执行只读能力探测，并为慢速或无响应设备设置超时。
5. 使用稳定标识合并已有别名、配置方案和最近状态。
6. 发布一次完整状态快照。
7. UI 根据能力决定控件是否可见或可用。

### 8.2 应用配置方案

1. 读取当前状态并保存可回滚快照。
2. 按稳定标识匹配显示器。
3. 缺少必要设备时停止，并向用户说明原因。
4. 验证模式、坐标、主屏和拓扑。
5. 生成系统显示变更计划。
6. 调用 `SetDisplayConfig` 提交系统配置。
7. 重新读取系统状态并确认结果。
8. 按显示器顺序执行已验证的 DDC/CI 设置。
9. 记录每项操作结果。

系统配置失败时不执行硬件写入。部分硬件写入失败时，保留已经生效的系统配置，并明确报告未完成项。

### 8.3 显示器热插拔

1. 接收显示变化事件。
2. 取消针对旧快照的后台任务。
3. 使用短延迟合并连续事件。
4. 重新枚举所有显示器和路径。
5. 重新探测新增设备能力。
6. 合并用户别名和配置方案。
7. 一次性刷新 UI。

## 9 可靠性和安全设计

| 风险               | 处理策略                             | 用户反馈                     |
| ------------------ | ------------------------------------ | ---------------------------- |
| 显示器热插拔       | 取消旧任务，短暂去抖后重新枚举       | 卡片自动更新，不弹出重复错误 |
| DDC/CI 长时间阻塞  | 每设备串行队列、超时和滑块写入合并   | 标记设备暂不可控并提供重试   |
| 提交无效拓扑       | 预验证路径和模式，保留原始快照       | 保持原配置并显示系统错误码   |
| 显示器身份变化     | 使用设备路径和 EDID 信息组合匹配     | 要求用户确认相似设备         |
| 配置导致画面不可见 | 保证至少一个活动屏幕，提供倒计时确认 | 未确认时自动恢复原配置       |
| 未知 VCP 行为      | 默认只读探测，写入功能使用白名单     | 高级功能标记为实验性         |

### 9.1 变更确认和回滚

分辨率、刷新率、方向、主屏和拓扑修改后显示确认倒计时。用户未确认、显示路径消失或应用失去预期状态时，恢复原始快照。

### 9.2 DDC/CI 调度

- 每台显示器只允许一个活动读写任务。
- 用户连续拖动滑块时只提交最新值。
- 读写操作设置超时，超时后释放句柄并重新探测。
- 失败次数达到阈值后暂停自动读取，避免持续卡顿。
- 显示器断开后立即取消关联任务。

## 10 权限 隐私和数据

软件仅控制当前登录会话中的本机显示设备。普通查询和多数配置操作不应要求管理员权限。不得通过常驻高权限服务扩大权限范围，除非某项经过验证的功能确实需要，并应将该功能单独隔离。

隐私要求：

- 不采集屏幕画面、窗口标题、键盘输入或用户文件。
- 设备别名、配置方案和日志保存在当前用户的应用数据目录。
- 诊断报告默认隐藏序列号和完整设备实例路径。
- 仅在用户主动导出时生成诊断报告。
- 不接入账号、广告、分析或云服务。
- 更新检查如需联网，应单独说明并允许关闭。

建议数据目录：

```text
%LOCALAPPDATA%/ScreenTools/
  settings.json
  profiles.json
  devices.json
  logs/
  diagnostics/
```

## 13 建议的解决方案结构

```text
apps/
  desktop/
    src/main/                       Electron 主进程
    src/preload/                    contextBridge 和 IPC 客户端
    src/renderer/                   Vue 3 界面
    electron-builder.yml            Windows 安装包配置

packages/
  contracts/                        IPC DTO Schema 和共享类型
  display-core/                     状态模型 方案匹配 变更计划
  display-control/                  TypeScript 系统控制服务
  display-native/                   Node-API Windows 原生模块
  profile-store/                    配置方案和 Schema 迁移
  diagnostics/                      日志 自检 脱敏报告
  ui/                               可复用 Vue 组件和样式

tests/
  e2e/                              Electron Playwright 测试
  hardware/                         显示器硬件验证工具

package.json
pnpm-workspace.yaml
pnpm-lock.yaml
tsconfig.base.json
```

包依赖方向保持单向：

```text
renderer → contracts ui
preload  → contracts
main     → contracts display-core display-control profile-store diagnostics
display-control → display-native
display-native  → Windows API
```

`display-core` 不依赖 Electron、Vue 或原生模块，以便用 Vitest 完整测试。`contracts` 不包含业务实现，只保存 IPC 数据结构、事件名称和运行时校验 Schema。

## 14 与参考项目的主要差异

LGwebOS-menubar 围绕单台 LG webOS 电视建立网络连接，并在连接后读取电视状态和发送命令。ScreenTools 面向本机的多显示器集合，设备生命周期由操作系统驱动，任何时刻都可能发生热插拔、模式重建或路径变化。

因此，ScreenTools 的核心不是网络连接会话，而是：

- 可重复生成的系统状态快照
- 每台显示器的能力矩阵
- 可验证的配置变更计划
- 失败后的回滚机制
- 系统事件驱动的重新枚举流程

参考项目的证书固定、配对密钥和局域网发现不适用于直接系统控制。应保留它的状态集中管理、命令日志、能力降级、本地隐私和离线自检思路，并将网络适配器替换为 Windows 显示配置与物理监视器适配器。
