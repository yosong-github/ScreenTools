# 画质增强 M0 性能验证

## 1. 目标

在开始实现「超分 + 插帧」之前，先验证 RTX 3060 Laptop 上的真实性能边界，回答三个问题：

1. RIFE 插帧能否满足 24/30fps → 48/60fps 的实时播放？
2. 超分应该处理到多高分辨率，再交给 GPU shader 放大？
3. DirectML 是否足够，还是必须引入 TensorRT / NCNN？

结论先行：**720p–900p 插帧 + 放大到 1440p/4K 可行；1080p 30→60 实时不可行；4K 插帧不可行。**

## 2. 测试环境

| 项目     | 值                                                                       |
| -------- | ------------------------------------------------------------------------ |
| GPU      | NVIDIA GeForce RTX 3060 Laptop，6GB 显存                                 |
| 驱动     | 591.59                                                                   |
| 系统     | Windows x64（VS Build Tools 18 / Windows SDK 10.0.26100）                |
| 推理后端 | ONNX Runtime DirectML 1.24.4，Python 3.12                                |
| 模型     | `NeoRIFE_v1_5_Lite50_fp16.onnx`（9.8MB，7 通道，fp32 输入/输出）         |
| 基准片段 | Big Buck Bunny 1080p60，取 `i-1` 与 `i+1` 插 `i`（等效 30→60），共 30 对 |
| 计时     | 稳态 15–30 次；含 CPU↔GPU 张量拷贝，不含视频解码、窗口捕获与显示         |

模型输入布局为 vs-mlrt RIFE v1 风格：

```text
[1, 7, H, W] = img0(RGB 0–1) + img1(RGB 0–1) + timestep(0.5)
```

宽高按 128 的倍数边缘复制补齐，例如 1920×1080 → 1920×1152，1280×720 → 1280×768。

> 该模型来自 cHiDeScaler-Neo 仓库。它在本机只用于性能验证；正式分发前必须确认模型来源与许可证，或改用可确认许可证的 RIFE 导出。

## 3. 性能

每对相邻帧执行一次推理，生成 1 个中间帧。实时预算：

| 输入 → 输出        | 每对帧预算 |
| ------------------ | ---------- |
| 24 → 48fps         | 41.7ms     |
| 30 → 60fps         | 33.3ms     |
| 24 → 60fps（2.5×） | 27.8ms     |
| 60 → 120fps        | 16.7ms     |

实测（DirectML）：

| 处理分辨率 | 实际输入（128 对齐） |       平均 |     P95 | 推理吞吐 |
| ---------- | -------------------- | ---------: | ------: | -------: |
| 960×540    | 1024×640             | **17.0ms** |  18.0ms | 58.9 fps |
| 1280×720   | 1280×768             | **22.8ms** |  25.0ms | 43.9 fps |
| 1366×768   | 1408×768             | **27.1ms** |  30.3ms | 37.0 fps |
| 1440×810   | 1536×896             | **31.1ms** |  31.9ms | 32.1 fps |
| 1600×900   | 1664×1024            | **38.5ms** |  40.8ms | 26.0 fps |
| 1920×1080  | 1920×1152            | **48.9ms** |  50.5ms | 20.5 fps |
| 2560×1440  | 2560×1536            | **90.5ms** | 105.3ms | 11.1 fps |

实拍片段逐帧推理（含预处理，30 对均值）：

| 处理分辨率 | 放大到    |   平均 |    P95 |
| ---------- | --------- | -----: | -----: |
| 1920×1080  | 不放大    | 53.3ms | 58.4ms |
| 1600×900   | 1920×1080 | 41.1ms | 45.3ms |
| 1280×720   | 1920×1080 | 25.1ms | 27.8ms |
| 960×540    | 1920×1080 | 18.6ms | 22.1ms |

结论：

- **30→60fps 只能在 720p（或 1366×768）稳定实时**，900p 超出预算。
- **24→48fps 可以用 900p**，720p 余量充足。
- **1080p 30→60 不实时**；即使去掉拷贝开销，仍明显超过 33ms。
- **1440p / 4K 插帧不现实**，应改为低分辨率插帧后由 FSR/Anime4K 放大。
- 60→120 只有 540p 擦边，不建议作为首批功能。

其他模型对照（1920×1080）：

| 模型                       |        平均 | 说明                |
| -------------------------- | ----------: | ------------------- |
| NeoRIFE v1.5 Lite50        |      48.9ms | 本次基准，最快      |
| NeoRIFE v1.5 Lite75        |      69.4ms | 质量更高，更慢      |
| NeoRIFE v1.2 / v1.5 / fp16 | 92.6–94.9ms | fp16 输入未带来收益 |
| 原始 RIFE FP32（6 通道）   |       175ms | 不适用实时          |

## 4. 画质

对 Big Buck Bunny 30→60 的中点插帧，使用原 60fps 帧作为真值：

| 处理方式                  |              PSNR 均值 | 说明                              |
| ------------------------- | ---------------------: | --------------------------------- |
| 1080p RIFE                |               36.77 dB | 细节最好，速度最慢                |
| 900p RIFE → Lanczos 1080p |           **37.21 dB** | 观感与 1080p 几乎无差别，速度更快 |
| 720p RIFE → Lanczos 1080p |               34.66 dB | 轻微变软，可接受                  |
| 540p RIFE → Lanczos 1080p |               31.64 dB | 明显变软，只建议低性能档          |
| 1080p 前后帧平均混合      | 24.66 dB（合成测试图） | 基线，运动处明显重影              |

900p 的 PSNR 略高于 1080p，是因为 Lanczos 放大平滑了部分插帧误差；这不代表 900p 细节更多。目视对比中，900p 与 1080p 基本一致，720p 在树叶、草地等高频区域略软，540p 可明显看出。

需要注意：

- 测试用的是 30fps 间隔（1/30s），**24fps 电影的运动间隔更大，遮挡和快速运动处的瑕疵会更多**，需要实片验收。
- 合成图案（testsrc2）只用于校验输入格式，画质结论以实拍片段为准。
- DRM 内容无法捕获；HDR 暂不支持。

## 5. 后端选择

- **DirectML**：可用，跨 NVIDIA/AMD/Intel，部署最简单；本机 1080p 约 49ms。
- **NCNN Vulkan**：CLI 端到端受 PNG 编解码干扰，未能隔离出纯推理时间；需要原生基准后再决定，暂不作为 M1 默认。
- **TensorRT**：RTX 20/30/40/50 可用，预计能显著提升 1080p，但需要额外 1–2GB 运行时，且仅 NVIDIA；建议作为后续「质量模式」的可选包。
- **纯 CPU**：不可行。

## 6. 对 M1/M2/M3 的约束

推荐预设：

| 预设 | 处理分辨率 | 适用输入 | 实测耗时 | 目标                      |
| ---- | ---------- | -------- | -------: | ------------------------- |
| 质量 | 1600×900   | 24fps    |     41ms | 24→48fps，放大到 1440p/4K |
| 均衡 | 1280×720   | 24/30fps |     25ms | 24→48 / 30→60fps          |
| 性能 | 960×540    | 24/30fps |     19ms | 弱 GPU 或高刷新输出       |
| 关闭 | —          | ≥60fps   |        — | 60fps 及以上不插帧        |

流水线预算：

```text
捕获 1 帧（WGC，约 1 帧延迟）
  → RIFE（720p/900p，19–41ms）
  → FSR/Anime4K 放大（<2ms，待实现时实测）
  → VSync 输出（1 帧）
```

- 视频播放可接受 1–2 帧延迟；**捕获任意程序时必须额外做音频延迟同步**（M3）。
- 24fps 内容建议默认「质量 900p」，30fps 默认「均衡 720p」，根据实际 GPU 负载自动降档。
- 1080p 插帧需要 TensorRT 质量包或更强 GPU，首版不承诺。
- 后续 M1 实测发现 `modernAnime` 比 FSRCNNX 更适合 2K 动画/CG 输出，且 1080p 插帧、先放大再插帧均不实时；见 [M1 的 2K 输出实测](enhance-m1.md#2k-输出实测)。
